01 · How it works

From a meter the utility already reads to a number anyone can check

Rooftop solar hides inside net load: the grid sees demand minus whatever the panels produce. Sunshine leaves a fingerprint in that series. We fit it, publish the exact inputs, and put the file's fingerprint on a ledger.

Off-chain · data and estimate

On-chain · BTMRegistry

1a

Net-load meter

Hourly MW at a grid station or region. The utility already records it.

1b

NASA POWER

Free satellite irradiance (GHI) and temperature for the same hours.

2

IRR estimator

Regress net load on hour × month, day type, degree terms and GHI × a smooth seasonal coefficient β(t).

hidden PV = β(t) × GHI

3

Evidence file + SHA-256

The exact inputs as a canonical CSV. Its SHA-256 changes if a single byte does.

4

BTMRegistry

The estimator wallet calls attest(): capacity, ±, recovery, evidence hash, code hash.

5

Regulator decides

setStatus() moves each estimate from Pending to Accepted or Disputed, with a note. In this demo a script plays the regulator.

6

Planners read it

Planners read latestAccepted(). Anyone can re-hash the file and call verify().

03 · Registry

Every estimate carries the fingerprint of its evidence

Each row is one attest() call to the BTMRegistry contract. The capacity is the model's; the hash pins the exact file it came from.

No regulator has reviewed these estimates. The statuses are a demonstration. The regulator role is played by an account the author controls, and a script accepts an estimate automatically when its in-sample recovery against AEMO is between 70% and 130%. That is a demo rule, not a regulatory review. The local demo also disputes one record whose evidence file it tampered with on purpose.

04 · Verify it yourself

Don't trust us. Re-hash the file.

Each button downloads the published evidence file, computes its SHA-256 in your browser and compares it with the station's reference hash: its latest accepted record in the registry, or the evidence manifest if nothing is anchored yet. Then change one reading by 1 MW and watch the fingerprint break.

verify.js · SHA-256 via WebCrypto · nothing you load leaves this browser

    Check a file you already have

    1. Use Download file above, then drop that file here: MATCH.
    2. Change one digit in a text editor, save, drop it again: MISMATCH.
    3. Re-save it with Windows (CRLF) line endings: also MISMATCH. The hash covers every byte, not just the numbers.

      05 · Honest limits

      What this does not show

      1. The headline recovery is in-sample. The model is fitted on the same year of net load and irradiance it is scored on; AEMO's rooftop PV is never used in fitting. The repository also reports a held-out split (fitted on odd months, scored on even months). Neither is a forecast test.
      2. Not every region is close. New South Wales and Queensland under-recover by about 26%. In New South Wales the shortfall is concentrated in summer, when sunshine and air-conditioning load rise together.
      3. The yardstick is itself an estimate. AEMO's rooftop-PV series is measurement-based (upscaled from metered systems), not a census of every roof.
      4. The ± is a seasonal spread, not a confidence interval. It is the standard deviation of twelve monthly capacity estimates.
      5. Small feeders are hard. On Pakistani household data (LUMS REWD-P, with PV of known size injected) the estimator recovers only about 33–40% for groups of 2 to 10 homes. It is meant for grid-station or DISCO scale, not a single street.
      6. A ledger proves integrity, not truth. The registry has not been deployed to a public network yet. The chain proves the evidence file was not changed after it was anchored; it does not prove the meter was honest or the model right. That is what a regulator's accept/dispute step and the open code are for; in this demo that step is a script, not a regulator.
      7. The charts are a slice. They show two weeks; the evidence files hold the full year.
